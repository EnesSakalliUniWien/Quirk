## Current alignment and detailed applicability

**Design principles:** Purpose is clearly circuit construction and scientific inspection; meaningful amplitude, phase, and density-matrix terms must survive simplification. Agency is supported by nonmodal inspectors, examples, keyboard alternatives and circuit undo, with PAT-01 as its bounded gap. Responsibility maps to preserving data and transparent browser clipboard/storage errors; no private-data or account feature is introduced. Familiarity maps to standard controls, platform shortcuts, consistent palette search and feedback; PAT-02 is its gap. Flexibility maps to adaptive panels, touch/pointer/keyboard, appearance and accessible numeric data; FND-01/02/03 bound the gaps. Simplicity already uses an Inspect menu, overflow and contextual options. Craft requires current tests and real device/AT verification, not historical pass counts. Delight should come from reliable scientific exploration; decorative animation, audio or haptics are not required.

**iOS:** Display/ergonomics/input/app-switching sections transfer to responsive browser layouts, comfortable touch targets, orientation changes and compact controls. Current adaptive dock and toolbar overflow support the primary-task requirement. Appearance preferences and contextual interactions are applicable; sensor/payment/biometric/Siri/widget/Home Screen capability lists are opportunities rather than requirements for this simulator. Physical small-screen reachability remains a device test gap.

**iPadOS:** Large-display content, reduced modality, combined touch/keyboard/pointer input, changing orientation and multitasking dimensions apply to browser use. Existing dock panels preserve the circuit context and grow into split areas at larger widths. Apple Pencil-specific native frameworks, widgets, and running an iPad binary on Mac are N/A. Viewing-distance comfort and physical pointer/touch combinations require device validation.

**macOS:** Spacious, movable/resizable panels and keyboard editing support long scientific tasks. Browser system windows/full screen remain browser-owned; native App menu, Dock menu and custom AppKit window prescriptions are N/A. Personalized dock layouts are already persisted. Supporting every arbitrary toolbar/font/color preference is not a requirement to build a settings system; the known font/contrast preference gaps have focused existing-token fixes.

**iPhone Duo:** Anatomy and Device poses explain inner/outer displays and folding, and inform available-size adaptation. Best practices and Dynamic layouts call for state/function continuity rather than per-pose custom interfaces. Current `AdaptiveDock.setNarrow` gathers/restores the same panel objects (`src/components/adaptive-dock.js:14-28,69-78,82-125`); regular panel renderers stay mounted ([src/components/dock.jsx:234](/Users/berksakalli/Projects/GitHub/EnesSakalliUniWien/Quirk/src/components/dock.jsx:234)). This is substantive source alignment with continuity, not a missing dynamic-layout implementation. Reserved regions/fold camera APIs need a native implementation or browser-provided viewport information; no evidence currently establishes that Safari exposes the cited native reserved-region model to this web app. Split views align with compact tabs versus wider split panels. Arrangement views are a native optional container; do not replace Dockview with a new browser layout abstraction. Vertical controls prescribe native system placement, not relocation of browser app toolbars merely because a native platform now arranges bars differently. Applicable shared intent is keeping frequent actions available, grouped and labeled as width changes; toolbar already has groups, aria-label/title/icon and More overflow (`app-toolbar.jsx:48-59,157-181,372`). Actual folded hardware, safe areas and camera activity are unverified. Do not claim iPhone Duo support from viewport resizing alone.

HIG: [Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo).

**tvOS:** The page's display distance, remote/focus input, cinematic content, multiuser and TV integrations describe a native television target. None is declared here; no gamepad, TV-provider accounts, parallax, audio or profiles should be added. General legibility/focus lessons are covered by Foundations/Inputs.

**visionOS:** Spatial windows, immersion/passthrough, eye/hand input, Spatial Audio, personal safety and comfort concern a spatial native target. Quirk is a 2D browser experience. Its Bloch sphere depicts scientific geometry and is not evidence of an immersive app. Minimum immersion is compatible with retaining a plain window. Native SharePlay/Personas, field-of-view placement and direct spatial gestures are N/A; browser accessibility and reduced motion remain applicable general lessons.

**watchOS:** Glanceable wrist tasks, Crown, Always On, complications, background sensors, notifications and standalone Watch functionality are N/A without a watch target. The whole circuit editor should not be forced into a one-screen watch workflow.

**Games:** Jump into gameplay/defaults/onboarding has transferable immediate-entry and optional-learning intent; no download-heavy game exists. Look stunning on every display / Enable intuitive interactions / Welcome everyone transfer readable text, responsive controls, input alternatives, numeric alternatives to color and accessibility. Apple's native point-size tables are not a direct CSS pixel compliance test. Game controllers, avatar representation, stories/stereotypes, Game Center, GameSave, haptic/audio/sensor mechanics in Adopt Apple technologies are N/A. Quirk is an exploratory simulator, not a game with competitive/social/player features.
